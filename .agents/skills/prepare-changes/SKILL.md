# Prepare Changes — разбиение запроса на проверяемые OpenSpec changes

Скилл **только анализирует и предлагает план** — не создаёт OpenSpec change, не пишет proposal/specs/design/tasks, не правит runtime-код.

**Содержимое отчёта:** предварительный план Change’ев (+ проверяемые результаты) и при необходимости блок **⛔ вне стека**. Без таблиц «решений разработчика» и опросников по продуктовым дефолтам.

## Норма: один change

**Один OpenSpec change — это нормальный и самый частый исход.** Не стремись разбивать «на всякий случай». Чаще всего запрос (включая client+server одной фичи) укладывается в **один** change с проверяемым результатом.

Дробить — исключение, когда без разбиения нельзя получить shippable/проверяемые куски (см. ниже). Prepare, который почти всегда предлагает 2–3 change без жёсткой причины — работает **неверно**.

Цель скилла: не раздувать один change **и одновременно** не дробить без нужды. Каждый предложенный change должен заканчиваться **проверяемым результатом** (тест, ручной сценарий, `openspec-verify-change`).

Следующий шаг после согласования плана — обычно [`openspec-propose`](../openspec-propose/SKILL.md) **по одному** change за раз (первый → implement/archive → следующий), либо явная просьба пользователя создать отдельный change.

## Когда применять

- Пользователь запускает `prepare-changes` / `prepare change` / просит подготовить разбиение scope
- Запрос выглядит широким («вся фича X», несколько экранов + контракт + контент), и нужно понять, один change или несколько
- Перед `openspec-propose` / explore, когда важно не свалить всё в один каталог

Не вызывать на мелкий багфикс с очевидным одним проверяемым исходом.

## Жёсткие принципы

1. **Default = один change (это норма).** Несколько — только при **жёсткой** причине (ниже). Не оптимизировать под «красивое» разбиение. Если сомневаешься — **один**.
2. **Проверяемый результат обязателен.** Если срез нельзя проверить сам по себе (полуконтракт без UI / UI без Rust API / reader без parse) — это не отдельный change, а часть соседнего или другой срез.
3. **Мало срезов лучше многих.** Если всё же дробишь: 2 типично, 3 редко, 4+ почти никогда. Не дробить по слоям «сначала schema, потом messages, потом UI» без самостоятельной ценности.
4. **Client+server одной фичи** обычно **один** change (вертикальный срез), не два репо-ченджа.
5. **Не invent scope.** Опираться на skills, specs, код. Неясности продукта/UX **не** разворачивать в таблицу «решений разработчика» — зафиксировать разумный default в «Делает» / «Не делает (out of scope)» или оставить на propose; не выдумывать лишние срезы.
6. **Вне стека = стоп-сигнал, не Change N.** Если часть запроса **нельзя** сделать в текущем стеке проекта (Flutter + Rust/FRB + локальный SQLite и канон skills/deps) — **явно подсветить**: нужно **изучить**, какой инструмент (lib / сервис / провайдер) подходит. Не прятать это в пункты работ и не предлагать «возьмём X» без изучения человеком.

## Когда РЕАЛЬНО дробить (иначе — один)

Дробить, если выполняется **хотя бы одно**:

| Причина | Пример |
|---------|--------|
| Независимые deliverable с разным «done» | (A) parse SRT + reader cues; (B) позже — vocab highlight by lemma |
| Промежуточное состояние должно быть shippable | Без A нельзя безопасно делать B; после A продукт уже лучше / не хуже baseline |
| Слишком большой blast radius для одного verify | Много capabilities + несвязанные UX-полировки + рефактор инфраструктуры |
| Разные риски / аудитории ревью | FRB API / SQLite vs чисто cosmetic Material chrome |

**Не** дробить только потому что:

- затронуты и client, и server
- в `.agents/AGENTS.md` много релевантных skills
- удобно писать tasks «по слоям»
- «так аккуратнее» без отдельного проверяемого outcome

- [`openspec-explore`](../openspec-explore/SKILL.md) — при необходимости уточнить идею; prepare сам не входит в explore-stance и **не** копирует из explore таблицы «решений разработчика»

## Workflow

```
Prepare-Changes Progress:
- [ ] 1. Понять запрос + active changes
- [ ] 2. Карта доменов (skills / specs / locate) + fit к стеку
- [ ] 3. Кандидатные срезы vs «один change»
- [ ] 4. Для каждого среза — пункты работ + проверяемый результат
- [ ] 5. ⛔ Вне стека / изучить инструмент (если есть)
- [ ] 6. Отчёт + рекомендация порядка; стоп (ждать согласия)
```

### 1. Понять запрос

- Сжать цель в 1–2 предложения.
- `openspec list --json` — если есть active change, явно сказать: новый план **рядом**, **вместо** (после archive), или **fold into existing** (тогда prepare может рекомендовать *не* дробить, а сузить/разбить tasks внутри одного — но это всё равно один change).
- Если запрос пустой — спросить, что готовить.

### 2. Карта доменов (обязательная опора)

1. По таблице skills в `.agents/AGENTS.md` отметить релевантные Flutter client (+ process) skills (имена + 1 фраза «зачем»).
2. Найти пересекающиеся capabilities в `openspec/specs/` (пути = capability ID).
3. При неоднозначности «где править» — кратко пройти `client-locate-change-points` и/или точечный поиск по `{app}/lib` и `{app}/rust`; в отчёте — 3–8 ключевых путей, не простыня.
4. **Fit к стеку** (обязательно): сверить запрос с deps (`pubspec.yaml`, `rust/Cargo.toml`), skills, `{app}/AGENTS.md`, существующими flows. Всё, что требует **нового** класса инструмента (обязательный online translate vendor, облачный sync словаря, PDF/видео-кодек, …) и **нет** канона в проекте — зафиксировать как кандидат в ⛔ (шаг 5), не как пункт работ change.

Зафиксировать:

- слои: Flutter `lib/` / Rust `rust/` / FRB bridge / только meta
- контракт: FRB API (`rust/src/api`) / только UI / только docs
- зависимости от уже существующего поведения
- **в стеке / вне стека** (кратко)

### 3. Решение: один или несколько

**Стартовая гипотеза всегда: один change.** Сформулировать его (scope + пункты работ + verify).

Дробить только если есть жёсткая причина из таблицы выше. Вопрос не «как красиво нарезать?», а «разве один change **нельзя**?» Если можно — **оставить один** и в вердикте так и написать (это успех prepare, не провал).

Если дробишь — минимальное число срезов, каждый с verify. Порядок = зависимости.

Для каждого среза: «можно ли проверить **после** этого change, не дожидаясь следующего?» Если нет — слить с соседом.

### 4. Пункты работ + проверяемый результат

Для **каждого** change обязательно:

1. **Пункты работ** — нумерованный список того, что входит в этот change (вертикальные куски scope: экран/контракт/schema/тест). Уровень: достаточно, чтобы человек понял границы и мог сказать «да/нет»; **не** расписывать файлы построчно и не писать полный `tasks.md` (это работа propose).
2. **Проверяемый результат** + **как проверить**.

Пункты работ должны покрывать «Делает» и не пересекаться с «Не делает». Обычно 3–8 пунктов на change; если пунктов >10 — срез, скорее всего, слишком большой (вернуться к шагу 3).

Для проверяемого результата указать **конкретный** способ, например:

- `flutter test` / `cargo test`: какие области / сценарии
- ручной: «открыть SRT → тап по слову → увидеть gloss / сохранить в словарь»
- `openspec-verify-change` против артефактов этого change

Плохо: «код написан», «схема обновлена», «UI частично готов».
Хорошо: «reader показывает cues из SRT; highlight сохранённых lemma работает; stub offline gloss ещё ок».

### 5. ⛔ Вне текущего стека — изучить инструмент

**Обязательная** проверка перед финальным отчётом. Если кусок фичи **нельзя** уверенно заложить в propose/apply в рамках текущего проекта:

| Сигнал | Пример |
|--------|--------|
| Нет подходящей lib / пакета в deps и нет канона «берём X» | загрузка изображений, PDF, видео-кодек |
| Нужен внешний сервис / провайдер без решения в docs/skills/env | online translate vendor, облачный sync словаря |
| Конфликт со стеком | другой UI-фреймворк, другая БД вместо on-device SQLite без решения |
| Нет контракта/паттерна в skills для класса задачи | «нужен инструмент под …», а в проекте аналога нет |

**Как подсвечивать** (заметный блок в отчёте, не прятать в пункт работ):

```markdown
## ⛔ Вне стека — нужно изучить инструмент

| ID | Что нельзя сделать сейчас | Чего не хватает в стеке | Что изучить / выбрать |
|----|---------------------------|-------------------------|------------------------|
| T1 | … | нет lib / нет провайдера / нет канона | класс инструментов: A/B/C (без «берём X» как факта) |
```

Правила:

- **Не** предлагать конкретный продукт как принятый, пока человек не изучил и не подтвердил (как в explore: agent-proposed new service → «изучили / ок?»).
- Такие пункты **не** становятся Change N «добавить lib X» без решения — либо out of scope плана, либо отдельный блок «после выбора инструмента → новый prepare/propose».
- Часть запроса, которая **в стеке**, планировать обычными Change 1…N; часть **вне стека** — только в ⛔.
- Если **весь** запрос упирается в T* — вердикт: сейчас **не prepare → propose**; сначала изучение инструмента.

Сверка с форматом ⛔ в [`openspec-explore`](../openspec-explore/SKILL.md); prepare обязан вынести это сам, даже без запуска explore.

### 6. Отчёт — стоп

Выдать отчёт по шаблону ниже: **только предварительный план + (при наличии) ⛔ вне стека.** Без секций «решения разработчика», списков D*/вопросов-блокеров и мини-explore.

**Не** вызывать `openspec-propose` / `openspec new change`, пока пользователь не согласится с планом (или не попросит сразу propose для Change 1). Если есть открытые T* (вне стека) по in-scope — **не** рекомендовать propose для затронутого куска.

## Шаблон отчёта

```markdown
# Prepare changes: <краткая цель>

## Вердикт
**Один change** (норма / ожидаемый исход) | **N changes** (N = …; исключение)
Почему: <1–3 предложения. Если один — достаточно «укладывается в один проверяемый deliverable, дробить не нужно». Если несколько — какая жёсткая причина.>

## Контекст
- Active OpenSpec: <нет | имена; рекомендация: fold / parallel / after archive>
- Пакеты: client / server / оба
- Релевантные skills: <список имён>
- Capabilities (существующие / вероятно затронутые): <paths>

## Карта кода (кратко)
- Client: `path` — …
- Server: `path` — …

## План

### Change 1 — `<kebab-name>`
- **Делает:** <1–2 предложения>
- **Пункты работ** (конкретный checklist scope; не полный `tasks.md`):
  1. …
  2. …
  3. …
- **Не делает (→ Change N / out of scope):** …
- **Проверяемый результат:** …
- **Как проверить:** …
- **Skills при apply:** …
- **Зависит от:** —

### Change 2 — `<kebab-name>` (если есть)
- **Делает:** …
- **Пункты работ:**
  1. …
  2. …
- **Не делает:** …
- **Проверяемый результат:** …
- **Как проверить:** …
- **Skills при apply:** …
- **Зависит от:** Change 1 (что именно должно уже быть)

## ⛔ Вне стека — нужно изучить инструмент (если есть)
| ID | Что нельзя сделать сейчас | Чего не хватает в стеке | Что изучить / выбрать |
|----|---------------------------|-------------------------|------------------------|
| T1 | … | … | … |

**Пока открыто:** не propose/apply для этого куска.
**Можно параллельно:** Change’ы по части запроса, которая уже в стеке (если ортогональна).

## Рекомендуемый порядок
1. Если есть T* — изучить/выбрать инструмент **или** вынести в out of scope
2. Согласовать план Change’ев
3. `openspec-propose` для Change 1 → implement → verify/archive
4. Затем Change 2 …
```

Если вердикт «один change» — секция плана содержит **только Change 1**; не выдумывать пустые Change 2 «на будущее». **Не извиняться** за один change и не предлагать «можно ещё порезать» без запроса пользователя.
Если есть T* — в вердикте явно: «часть / всё вне стека до изучения инструмента».
**Не** добавлять в отчёт таблицы/секции «решения разработчика», «открытые вопросы», D*-блокеры — это зона explore/propose, не prepare.

## Связь с другими скиллами

| После prepare | Skill |
|---------------|--------|
| Уточнить идею (по желанию пользователя) | [`openspec-explore`](../openspec-explore/SKILL.md) |
| Создать артефакты **одного** согласованного change | [`openspec-propose`](../openspec-propose/SKILL.md) |
| Реализация | [`implement-change`](../implement-change/SKILL.md) / [`openspec-apply-change`](../openspec-apply-change/SKILL.md) |
| Проверка | [`openspec-verify-change`](../openspec-verify-change/SKILL.md) |

Prepare **не** заменяет explore (мышление) и **не** заменяет propose (артефакты). Он только режет scope на shippable куски и флагует внестековые инструменты.

## Guardrails

- Не создавать каталоги в `openspec/changes/` и не писать proposal/specs/design/tasks из этого скилла
- Не дробить «по репозиторию» или «по skill-файлу»
- Не предлагать срез без проверяемого результата
- Не раздувать до micro-changes (один экран / одна колонка / один тест)
- При сомнении — **один** change + чёткий Out of scope, а не два полусреза
- **Не** стремиться разбивать: один change — норма; несколько — только по жёсткой причине из таблицы
- **Не** маскировать «нужна новая lib/сервис» под пункт работ Change N — только блок **⛔ Вне стека — нужно изучить инструмент**
- **Не** навязывать конкретный инструмент как решение, пока человек не изучил и не подтвердил
- Внестековые пробелы без канона в проекте — формат ⛔ T*; не маскировать под «Change N разберётся»
- **Не** писать в отчёте «решения разработчика» / D*-таблицы / опросники по UX-дефолтам — только план и (при необходимости) ⛔ вне стека
